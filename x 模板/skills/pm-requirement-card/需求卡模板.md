> 用途：用于记录一个可以进入讨论、原型或开发协作的单个需求。默认保持轻量，最终成稿应像一张清晰的需求卡，而不是一份完整 PRD。

## 1. 需求背景

说明为什么现在要做。这里不要只写功能诉求，而要写清楚当前问题、影响对象和本次处理价值。

推荐结构：

> 当前【对象 / 模块】在【场景】下存在【具体问题】，导致用户在【判断 / 操作 / 协作 / 交付】上产生成本。本次优化重点是【本次要解决的核心问题】，不改变【本次不准备触碰的基础规则】。

写作要点：

1. 用 1-2 段即可，不需要长篇背景。
2. 先讲工作问题，再讲界面或功能。
3. 如果需求来自 demo 对齐、线上反馈、会议结论或开发实现差异，要点明来源。
4. 避免只写“为了优化体验”“需要新增一个能力”“按设计稿实现”。

示例：

> 工作台左、右栏已改为树形结构后，资源和结果的层级关系更清晰，但也带来两个问题：用户无法快速看到当前工作台内各类资源、结果的总量；多层级树结构在 3 级以上时，节点名称展示空间不足，影响识别和操作。
>
> 本次优化重点是提升工作台左右栏的浏览效率和空间可调性，不改变资源、结果本身的组织方式。

---

## 2. 目标场景

用一段话描述用户在什么场景下，用这个能力解决什么问题。

推荐结构：

> 用户在【业务场景】中，可以【完成的关键动作 / 获得的关键判断】；当出现【高频边界场景】时，可以通过【本次能力】继续完成工作。

写作要点：

1. 场景要能看出用户、工作任务和预期结果。
2. 不要把功能清单搬到这里。
3. 如果一个需求只有一个核心场景，用一段话即可。
4. 如果有两个以上明显不同的场景，可以用短列表，但不要展开成完整流程文档。

示例：

> 用户进入工作台后，可以快速判断当前工作台中资源和结果的数量分布；当树层级较深或名称较长时，可以通过调整栏宽或分区高度，获得更合适的查看空间。

---

## 3. 本次做什么

这是需求卡的主体。按对象、模块、状态或用户动作拆开写，复杂规则尽量放在表格里。

### 3.1 功能点名称

先用一句话说明这个功能点解决什么问题，然后用表格或列表写清楚具体规则。

适合表格的场景：

- 多对象：例如资源分类、文件夹节点、结果分类。
- 多状态：例如排队中、解析中、失败、成功。
- 多操作：例如批量操作、单条操作、操作后状态。
- 多口径：例如标题数量、文件夹数量、递归统计范围。

表格示例：

| 对象 | 展示方式 | 统计口径 |
| --- | --- | --- |
| 资源分类 | 分类名称右侧展示数量 tag | 统计该分类下解析成功的文件数量 |
| 文件夹节点 | 文件夹名称右侧展示数量 tag | 统计该文件夹及所有子级文件夹下解析成功的文件数量 |

说明：

- 文件分类标题数量仅统计解析成功的文件。
- 文件夹数量包含所有子级文件，不只统计当前层级。
- 排队中、解析中、失败文件仍通过状态区展示，不计入文件树数量。

### 3.2 功能点名称

根据实际需求增减小节。小节标题应直接对应功能对象或用户动作，不建议使用过抽象的标题。

写作要点：

1. 功能描述写“用户看到什么 / 能做什么 / 系统如何反馈”。
2. 规则紧贴功能点，不要把规则单独堆到最后。
3. 数量、状态、默认值、上下限、递归范围、失败态、清空范围、是否记忆等都要写成明确口径。
4. 如果某个功能只有一句话能说清楚，不必强行做表格。

---

## 4. 本次不做什么

写清楚边界，避免范围扩张。这里不是未来规划，而是本次明确排除的内容。

常见写法：

1. 不调整已有基础规则。
2. 不新增相关但非必要的配置能力。
3. 不改变现有数据结构或历史数据。
4. 不处理与本需求无关的历史遗留问题。
5. 不做跨刷新、跨设备、跨用户记忆，除非本次明确要求。
6. 不改变现有视觉风格，只补齐交互、状态或口径。

示例：

1. 不调整资源和结果的树形层级规则。
2. 不新增资源或结果的筛选、排序能力。
3. 不改变文件解析状态的判断逻辑。
4. 不做数量统计的高级配置，例如按状态、类型、时间范围切换统计口径。

---

## 5. 验收口径

用 3-8 条描述“做到什么程度算完成”。每条都应该可以通过 demo、测试或人工操作验证。

推荐写法：

1. 用户进入【页面 / 模块】后，可以看到【明确内容】。
2. 当用户【点击 / 拖拽 / 选择 / 提交】后，【系统表现】发生可见变化。
3. 【数量 / 状态 / 结果】与【指定口径】一致。
4. 在【边界情况】下，不出现【遮挡 / 误计数 / 错误操作 / 数据丢失】。
5. 【刷新 / 返回 / 重试】后，系统按【明确规则】恢复或保持。

示例：

1. 用户进入工作台后，可以在资源分类、资源文件夹、结果分类、结果文件夹上看到数量 tag。
2. 左栏“文件”数量与文件树内可见解析成功文件数量口径一致。
3. 文件夹数量应包含所有子级文件夹内的文件或结果。
4. 左栏和右栏支持横向拖拽，拖拽后宽度发生可见变化。
5. 拖拽到边界时不遮挡主要内容，不影响树节点展开、收起、选择、搜索和菜单操作。
