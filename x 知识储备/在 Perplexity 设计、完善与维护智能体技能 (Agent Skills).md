# 在 Perplexity 设计、完善与维护智能体技能 (Agent Skills)

**2026年5月1日**

Perplexity 的前沿智能体产品建立在封装为模块化“**智能体技能（Agent Skills）**”的诀窍（know-how）和领域专家知识的基础之上 。我们在技术环境中维护着一个精心策划的技能库 。这些技能包括驱动 Perplexity Computer 的许多通用公用程序、金融、法律和健康等领域的特定垂直能力，以及用于解决用户需求的大量长尾模块 。有些技能虽然很少被调用，但在调用时至关重要 。

为了确保始终如一的卓越用户体验，Perplexity 的智能体团队对**技能质量**的重视程度与代码质量并重 。开发高质量技能所需的直觉和最佳实践与构建传统软件显著不同 。智能体团队经常审查由优秀工程师在工作过程中开发的技能 PR（拉取请求） 。其结果几乎总是会产生大量的修改意见和建议 。这是因为许多有用的代码编写模式在技能创作中反而变成了**反模式（Antipatterns）** 。

例如，如果你拿《Python 之禅》（PEP20）中的格言来对比，就会发现编写好的 Python 代码与编写好的技能完全不同 。在 20 条智慧中，至少有一半在编写技能时是完全错误或具有误导性的 。以下是其中的五条 ：

Python 之禅 vs. 技能之禅

|**Python 之禅 (Zen of Python)**|**技能之禅 (Zen of Skills)**|
|---|---|
|**简约胜于复杂 (Simple is better than complex)**|**技能是一个文件夹，而非文件。复杂性正是其特性。**|
|**显式胜于隐式 (Explicit is better than implicit)**|**激活是隐式的模式匹配。采用渐进式披露。**|
|**稀疏胜于稠密 (Sparse is better than dense)**|**上下文是昂贵的。追求每 token 的最大信号量。**|
|**特殊情况不足以特殊到破坏规则**|**“坑（Gotchas）”正是特殊情况（它们是最高价值的内容）。**|
|**如果实现容易解释，可能是个好主意**|**如果实现容易解释，模型早已知晓。直接删掉它。**|

---

什么是技能？

编写技能时，你不是在写传统的软件（尽管技能现在是智能体系统主要逻辑引擎的一部分） 。相反，你是在为模型及其环境**构建上下文（Context）** 。技能有着不同的约束和设计原则 。如果你像写代码一样写技能，你将会失败 。

在 Perplexity 的构建语境下，一个技能至少包含以下四个方面 ：

1. 技能是一个目录

技能不只是一个单独的 `SKILL.md` 文件。在许多情况下，一个技能包含多个文件 。在以你的技能命名的目录下，你可能会看到 ：

- **`SKILL.md`**：前置元数据（frontmatter）和指令 。
    
- **`scripts/`**：智能体运行的代码，而不是让它重新发明轮子 。
    
- **`references/`**：重头文档，仅在满足条件时加载 。
    
- **`assets/`**：模板、Schema（架构）和数据 。
    
- **`config.json`**：用户首次运行的设置 。
    

这种“轴辐式（hub-and-spoke）”模式可以让你保持技能的聚焦和紧凑，并且可以非常创意地利用文件夹结构 。有时，特别复杂的技能受益于**多层级结构**，以帮助模型更好地导航 。

- 假设一个技能需要涵盖 300 个主题，这些主题可以分为 20 个领域 。
    
- 即使对于当今最强的前沿模型，从 300 个主题中准确选择一个也是一项尚未解决的挑战 。
    
- 相比之下，让模型先定位到 20 个领域中的一个，再从该领域内的 15 个主题中选择，是一个容易得多的选择题 。
    
- **案例：** 我们的团队在去年税收季为 Computer 的美国个人所得税技能采用了三层主题嵌套 。由于税法的复杂性，这种层级结构是必不可少的：在早期测试中，向模型提供一个包含美国国税法（Internal Revenue Code）全部 1,945 个章节的单一文件夹，其表现比不加载技能还要差。将信息组织成逻辑细分领域对于确保高精度的读取操作至关重要 。
    
- 然而，这种层级结构并非没有代价。增加层级需要跨信息架构进行更高水平的策划（curation），以管理由此产生的间接性 。我们设计了快速参考指南、自定义搜索工具和其他工具，以支持模型以最少的间接性定位信息 。在这种情况下，艰苦的策划工作最终产生了积极的结果：该技能使模型能够比仅使用通用工具更胜任税务相关任务 。
    

2. 技能是一种格式

技能是一种格式。核心根目录下的 `SKILL.md` 文件必须同时具备**名称**和**描述** 。

- 此外，技能必须与所在的目录名严格匹配 。
    
- **名称**：必须全小写，无空格，可以使用连字符 。
    
- **描述**：这是**路由触发器（Routing Trigger）** 。这是一个常见的失败点：描述不是关于技能用途的内部文档 。它等同于给模型的指令，告诉它何时加载该技能 。因此，你会经常看到“Load when...（在……时加载）”，而不是“This Skill does...（此技能的作用是……）” 。这很重要，因为大多数实现会将描述注入到模型上下文中 。
    
- 在前置元数据中，还有 `depends:` 字段（用于创建层级技能依赖关系）和 `metadata:` 字段（用于审查和评估） 。不同的智能体系统甚至可以定义自己的前置元数据字段 。
    
- 作为替代方案，特定技能的元数据可以封装在辅助的 JSON 或 YAML 配置文件中 。当构建需要根据每个技能促进不同运行时行为、且不希望用细节污染模型上下文的智能体系统时，这是理想的选择 。
    
- 最后，通过在读取时剥离技能的前置元数据，可以获得类似的行为 。Computer 采用了这种方法，允许配置保留在根目录的 `SKILL.md` 文件中 。解析逻辑需要精细的处理，如果某些字段在模型上下文中有用，可能需要实现条件剥离 。
    

3. 技能是可调用的

技能是可调用的（Invocable）。智能体在运行时加载技能 。重要的是，技能并不总是捆绑在上下文中。默认情况下，大多数智能体系统会根据具体需求**渐进式**地展开技能 。在 Computer 的实现中，至少有三个层级的上下文成本 。过程如下 ：

1. Computer 调用 `load_skill(name="...")` 。
    
2. Computer 将技能目录复制到隔离的执行沙箱中 。
    
3. Computer 递归地自动加载 `depends:` 标签中的依赖项 。
    
4. Computer 随后剥离前置元数据，因此智能体只能看到主体内容和附加文件 。
    

不同的智能体系统可以选择以不同的方式暴露技能内容 。例如，有些系统可能选择完全不暴露文件层级，让模型通过文件系统操作自行发现 。其他系统可能选择向模型提供截断或限制深度的完整文件树映射 。为了保持上下文整洁，Computer 在调用上下文中省略了完整的文件层级；不过，这在单个技能的基础上是可以覆盖的 。

4. 技能是渐进的

技能是渐进的。在 Computer 中，有三个不同层级的上下文成本，我们在不同阶段承担这三种成本 ：

|**层级 (Tier)**|**加载内容**|**预算**|**支付时机**|
|---|---|---|---|
|**索引 (Index)**|每个非隐藏技能的名称和描述|每个技能约 100 tokens|每个会话、每个用户，始终支付|
|**加载 (Load)**|`SKILL.md` 全文主体|约 5,000 tokens|智能体决定调用 `load_skill()` 时|
|**运行时 (Runtime)**|`scripts/`、`references/` 等附件|无限制|仅当智能体实际读取它们时|

- **索引层级**：Computer 构建了一个包含所有可用技能名称和描述的索引 。预算约为每个技能 100 tokens（越短越好） 。这非常紧张，因为你在每个用户的每个会话中都要支付这笔费用 。它在对话开始时就被注入到系统提示词中 。模型据此决定是否调用 `load_skill()` 。进入这个索引的门槛极高 。
    
- **加载层级**：加载技能后，会有完整的 `SKILL.md` 主体。理想情况下不应超过 5,000 tokens 。即使如此，你也希望每一句话都发挥作用，因为一旦加载，后续对话都要承担这个成本，直到达到压缩边界 。许多对话会加载 3 到 5 个不同的技能，使成本翻倍 。废话连篇的技能几乎肯定会降低其他技能及整体智能体能力 。
    
- **运行时层级**：这是脚本、子技能或特殊格式所在的地方 。这里适合放置**无限制的条件分支逻辑** 。智能体只有在需要时才会使用它，这意味着这里的门槛要低得多 。
    
- **总结**：在索引中，每个 token 都至关重要。加载的技能主体相对宽松，而运行时则是最宽松的 。这部分可能是 20,000 tokens，也可能是 0 tokens，这是你以渐进方式扩展模型上下文的层面 。

什么时候需要技能？

智能体团队经常被问及某个领域或用例是否真的需要技能 。我们很少能仅凭基本原则给出确定答案 。唯一的方法是先启动不带技能的智能体，运行几个核心查询（hero queries），看看它的表现如何 。

何时需要技能

- 当你想以某种特定方式改变模型默认行为，且无法通过简短的提示词实现时 。
    
- 当智能体在没有特殊上下文的情况下会出错，或者你需要跨运行保持极高的一致性或确定性时 。
    
- 当你的知识是持久的，但不在模型的训练数据中（如企业特定工作流、截止日期后的信息） 。
    
- **案例：** 我们的设计主管 Henry Modisett 编写了几个设计相关的技能 。这些技能中的每个 token 都很重要，因为 Henry 在网站和 PDF 设计方面有着极佳的品味 。他指定了字体的选择与禁忌、字体的感觉等判断性问题，这些是模型无法仅从训练数据中学习到的 。
    

何时不需要技能

- 如果你只是写了一系列需要按顺序执行的 `git` 命令，那是不必要的。模型已经知道怎么做了，这作为文档很好，但作为技能很烂 。
    
- 如果只是在重复系统提示词中的指令 。
    
- 如果知识对大多数请求都相关，应该包含在全局上下文中，而不是条件加载的技能中 。
    
- 布莱斯·帕斯卡（Blaise Pascal）曾在 1657 年写道：“我把这封信写得更长了，只是因为我没有时间把它写得更短。” 。
    
- 正如帕斯卡所言，你需要投入时间在每个技能上 。写出一个精简的技能很难 。如果你的技能很容易写就，它可能太长了，或者根本不该存在 。好的技能应尽可能简短 。
    
- **警告**：如果你想在五分钟内通过 LLM 一次性生成技能并提交 PR，结果注定平庸 。研究显示，模型往往无法可靠地编写它们自身能从中受益的程序性知识 。

如何构建技能：步骤指南

你需要将你的主观见解（Opinion）注入到你编写的技能中 。请遵循以下步骤 ：

步骤 0：编写评估 (Evals)

先写评估案例。来源包括 ：

- **真实用户查询**：从生产环境或你的智囊团中采样 。
    
- **已知失败案例**：因为缺少技能而导致的失败 。
    
- **邻近领域混淆**：接近你的领域边界但应路由到其他技能的案例 。
    
- 测试技能是否在需要时加载 。**负面示例往往比正面示例更强大** 。
    

步骤 1：描述

这是技能中最难的一行。它是一个路由触发器，而不是文档 。

- 你唯一关心的应该是技能是否在正确的点被加载，且没有 off-target 的副作用 。
    
- 每增加一个技能，都有可能让其他技能变差，因此要最小化回归风险 。
    
- **不要**写技能做了什么，而要写智能体**何时**应该加载它 。
    
- **示例**：如果是监控 PR 的技能，不要描述功能，要写工程师想确保 PR 成功时会说的话，如“babysit”或“watch CI” 。
    
- **清单**：以“Load when...”开头；目标 50 字以内；描述用户意图 ；不总结工作流 。
    

步骤 2：编写主体内容

向 LLM 传达工作流与向同事传达完全不同 。

- 对于存在超过一年的软件工具，只需提到名字，LLM 就有它所需的所有信息 。
    
- **跳过显而易见的事实** 。不要写出所有命令的列表 。
    
- **示例**：不要写具体的 `git log; git checkout ...` 。而要写：“将提交 cherry-pick 到干净的分支。在保留意图的前提下解决冲突。如果无法顺利落地，请解释原因。” 。
    
- 模型在应对灵活指导时表现更好，尤其是在出错时 。**不要把模型限制死（Railroad）**，要在多种方法都可行时保持灵活性 。
    
- 重点放在“**坑（Gotchas）**”或负面示例上 。这些是极高信号的内容，因为它们告诉模型**不要做什么** 。
    

步骤 3：利用层级结构

- **`scripts/`**：放置智能体每次都会重复发明的确定性逻辑。给它代码去组合，而不是去重建 。
    
- **`references/`**：重型文档，仅在满足条件时加载（例如：“若 API 返回非 200，则读取 api-errors.md”） 。
    
- **`assets/`**：输出模板或 Schema 。
    
- **`config.json`**：首次运行的用户设置（如询问 Slack 频道并保存） 。
    

步骤 4 & 5：迭代与发布

在分支上进行大量测试，运行评估集 。描述中的微小改动可能对路由产生“远距离作用”的影响，务必在发布前解决 。

如何维护技能

“坑”的飞轮 (The Gotchas Flywheel)

从此时起，你的“坑”列表往往会大幅增长或变化 。技能应该是“仅限追加（append-mostly）”的。随着时间推移，“坑”部分积累的价值最高 ：

- **智能体失败了？** -> 增加一个“坑” 。
    
- **智能体错误加载了？** -> 收紧描述并增加负面评估 。
    
- **智能体没加载？** -> 增加关键词和正面评估 。
    
- **系统提示词变了？** -> 检查是否有冲突或重复 。
    

这是一种负面示例，它并不改变显式指导，但让模型知道“嘿，这里有一个已知失败案例” 。随着你从 80/20 走向 99.99% 的成功率，这个列表会不断增长 。

评估套件

我们运行多种评估套件：

- **加载与读取评估**：检查技能加载的准确率、召回率和禁用检查 。
    
- **渐进式加载评估**：智能体加载了技能，但它是否读取了必要的附件（如 `FORMATTING.md`）？
    
- **端到端评估**：运行完整闭环，并使用 **LLM 裁判**根据标准打分 。
    
- **多模型评估**：在 GPT、Claude Opus 和 Claude Sonnet 上运行。Sonnet 和 GPT 在处理技能时的行为差异很大 。

结语与要点总结

- 越早开始自动化你的日常任务越好。任何每周、甚至每季度重复的工程任务，都应该尝试将其自动化为智能体技能，以买回你的时间 。
    
- **少即是多** 。
    
- **先写评估**，包含负面示例 。
    
- **描述最难**，“Load when...”中的每个字都在消耗注意力 。
    
- **“坑”是最高价值的**。从小处开始，随着智能体的失败而成长 。
    
- **警惕远距离作用**。新技能可能在不经意间破坏旧技能 。
