## 1. 总体结论

当前 `DESIGN.md` 是有效的“设计语言宪法”，不是无效文档。它已经稳定约束了产品气质：白色工作台、浅灰/浅蓝布局、蓝色主色、高信息密度、桌面优先、低噪阴影、8/12/24 间距、22/20/18/14/12 字阶、8/12 圆角。这些原则在工作台、技能库和审计助手主界面中都有明显体现。

但它目前还不是一份完整的“可执行设计系统契约”。核心问题不是写得太少或太抽象，而是它和运行时代码已经发生漂移：

- 文档定义的主色是 `#0075de`，运行时代码实际使用 `#1677ff`。
- 文档只列出 42 个 `--ds-*` 相关 token 线索，运行时 `runtime-ui.css` 定义了 272 个 token；其中大量运行时稳定角色没有进入文档。
- 文档对通用组件原则写得清楚，但没有把组件原语和真实实现约束起来，导致有些 Vue 组件存在但页面并不使用。
- 业务 CSS 的硬性治理状态良好，脚本显示 `should-fix=0`；偏离主要集中在 review 级的一次性间距、行高、局部阴影、z-index 和组件调用口径。

我的判断：`DESIGN.md` 对“设计语言”的作用约为 80%，对“token 与实现一致性”的作用约为 60%，对“组件复用约束”的作用约为 45%，对“后续新增页面防漂移”的作用约为 65%。它已经能防止大方向跑偏，但还不能充分防止局部实现逐步漂移。

## 2. 外部调研：Design.md 应该管什么

这里的 `DESIGN.md` 不应该被理解成“每个页面的逐像素说明书”，而应该是设计系统在代码仓库里的可执行摘要：它定义统一性的标准、设计语言、可选范围、组件契约和例外治理。

几个主流设计系统给出的共同规律：

1. 设计系统先定义有限选项，而不是开放值域。USWDS 说明设计 token 的价值在于把颜色、字号、行高、间距等无限可能收敛为有限集合，减少设计和开发沟通成本。[USWDS Design tokens](https://designsystem.digital.gov/design-tokens/)

2. token 应表达角色，而不是只表达数值。Material 3 把颜色、字体、形状都作为角色系统：例如颜色角色决定某个颜色用于哪里，角色可以映射到不同值，但不能乱用，否则会损失可访问性。[Material 3 theming codelab](https://developer.android.com/codelabs/m3-design-theming?hl=en)

3. token 分层是主流做法。Primer 把颜色 token 分为 base、functional、component/pattern：base 不应直接用于设计和代码，functional 承载文本、边框、背景、阴影等全局角色，component/pattern 用于更具体的组件场景且数量应受限。[Primer Color usage](https://www.primer.style/product/getting-started/foundations/color-usage/)

4. 组件专属 token 可以存在，但不能变成全局语言。Carbon 明确 component tokens 只服务特定组件，不应当拿去做全局 token。[Carbon Color tokens](https://carbondesignsystem.com/elements/color/tokens/)

5. 间距、字号、圆角不是越全越好，而是要形成尺度。Carbon 的 spacing scale 用 2/4/8 的倍数体系，同时覆盖组件内部小间距和布局密度控制。[Carbon Spacing](https://carbondesignsystem.com/elements/spacing/overview/)

6. 组件和模式要区分。GOV.UK 把 Styles、Components、Patterns 分开：组件是可复用 UI 部件，模式帮助完成常见任务。[GOV.UK Design System](https://design-system.service.gov.uk/) 这说明特化业务结构不一定都要组件化，但反复出现的结构应该沉淀为 pattern。

7. 不是所有上下文特化结构都应进入核心组件库。Primer 的贡献指南强调：新 pattern 要先审计相似模式、考虑复用场景；只服务单一上下文的 pattern 不太适合作为 reusable component。[Primer contribution design guide](https://primer.style/product/contribute/design/)

8. 设计 token 是跨设计工具和代码平台共享视觉语言的标准化载体。DTCG/W3C Community Group 的目标是让团队能可靠共享视觉语言。[Design Tokens Community Group](https://www.designtokens.org/)

因此，你的理解是对的：`DESIGN.md` 应该延续传统设计系统，但不需要定义所有新样式和特化布局。它应该约束“怎么判断一个新样式仍然属于这套产品语言”，而不是替代每次具体页面设计。

## 6. 设计系统应如何定义：建议框架

建议把 `DESIGN.md` 从“纯设计宪法”升级为“设计语言 + 工程契约”，但不要变成大而全的 PRD。

推荐结构：

1. 适用范围与不适用范围  
   说明只服务综合分析平台当前高保真原型，不默认外溢到其他产品；说明桌面优先。

2. 产品视觉语言  
   保留“白色工作台 + 企业级分析工具”，明确不是营销页、不是数据大屏、不是纯聊天产品。

3. Foundation  
   色彩、字体、间距、圆角、阴影、z-index、动效、图标。每类都写：
   - 可选范围
   - 使用角色
   - 禁止项
   - 例外条件

4. Token 分层  
   明确：
   - primitive token：只在 foundation 内使用，不直接给业务 CSS 消费。
   - semantic token：业务 CSS 优先使用。
   - component token：只服务对应组件。
   - context token：只服务特定页面场景，如 L1 hero / audit workbench。

5. 通用组件契约  
   对 PageShell、Hero、InfoRail、Trigger、Search、Button、Tag、StatusPill、Table、ModalFooter、Drawer 写最小契约：
   - 何时必须用
   - 允许的变体
   - 禁止的变体
   - 真实代码入口

6. 产品级 Pattern  
   写工作台列表、技能库列表、审计助手三栏、技能配置编辑器。这里不需要逐像素定义，但要定义边界：
   - 可以特化什么
   - 必须复用什么
   - 何时应沉淀成通用组件

7. 例外机制  
   允许特化布局存在，但必须满足：
   - 使用现有 semantic token
   - 不新增裸色/裸阴影/临时字号
   - 不破坏控件高度、文字层级、状态色语义
   - 同类结构第二次出现时，考虑沉淀 pattern

8. 验证口径  
   明确默认检查：
   - `node scripts/check-manifest.js`
   - 三个主路由 smoke：`#project`、`#template`、`#freeaudit?projectId=PRJ-2026-001`
   - 必查状态：hover、focus-visible、selected、disabled、empty、loading、modal footer、长文本溢出。

3. 定义技能配置编辑器模式：双栏、文件树、内容编辑、校验状态。

### P3：加强治理脚本

1. 增加未定义 token 引用检查，当前发现 `--ds-type-icon-symbol-lh` 被 JS 使用但运行时未定义。
2. 增加 `runtime-ui.css` 非 root 区裸色扫描，把 foundation token 定义和组件样式区分开。
3. 增加 z-index token 使用审查，避免 `10 / 25 / 1110 / 3100` 继续扩散。
4. 增加主路由 smoke 文档化，不一定每次自动化，但报告口径要固定。

## 8. 最终评估

你的判断基本正确：设计系统不是要决定所有新页面的细节，也不应该把每个特化布局都写死。它真正约束的是统一性标准和设计语言，包括颜色角色、字号层级、间距尺度、圆角范围、阴影深度、组件行为和模式边界。

对当前综合分析平台来说，`DESIGN.md` 应该从“审美方向文档”往前走一步，成为“设计语言 + 代码消费规则”。最重要的不是把内容写得更长，而是把三层关系讲清楚：

- 哪些是不可突破的 foundation。
- 哪些是可复用组件和模式。
- 哪些是允许在业务场景里特化的局部设计。

现状不是糟糕，而是进入了第二阶段：视觉方向已经稳定，下一步要解决的是“文档、token、组件、检查脚本”四者的对齐。只要先修主色/文字语义漂移，再补 token 分层和组件契约，后续新原型会明显更不容易跑偏。
