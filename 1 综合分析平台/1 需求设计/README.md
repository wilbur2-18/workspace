# 综合分析平台 · 需求设计

本目录承载综合分析平台的需求卡、设计约束和高保真原型。这里是产品需求进入原型与开发协作前的工作区，不要求所有内容都按固定文件名维护。

## 当前内容

| 类型 | 说明 |
| --- | --- |
| 需求卡 | 统一放入 `需求卡/`，通过文件名前缀和卡片正文状态管理。 |
| 设计约束 | `DESIGN.md` 记录当前综合分析平台原型的视觉和组件约束。 |
| 高保真原型 | 当前可演示静态原型以本目录实际存在的最新原型目录为准；当前本体为 `综合分析平台 20260616/`，方案分支为 `综合分析平台 20260611（分支）/`。 |
| 待梳理材料 | 仅限与需求卡或原型交付直接相关的临时说明，按真实工作需要保留。 |

## 协作方式

- 修改需求前，先确认需求卡或相关说明是否已存在。
- 新增或更新需求卡时，先进入 `需求卡/`，并同步更新文件名前缀和卡片正文状态。
- 修改原型前，先读目标原型目录的 README 和 `DESIGN.md`。
- 不根据旧版本目录名推断当前入口；以当前目录实际存在的原型目录为准。
- 后续原型优化按“本体 / 分支”并行维护：本体承载相对稳定、准备延续的主方案；分支承载备选方案、局部探索或对比实验。
- 开始修改前先确认目标是本体还是分支；除非明确要求合并，不把分支试验内容同步回本体，也不把本体调整自动复制到分支。
- 当分支方案被采纳时，再按具体差异回合并到本体，并补充必要的验证说明。
- 需求层面的关键决策跟随需求卡维护，不单独拆出难维护的决策目录。
- 与原型设计无关的系统架构讨论、材料汇总、一次性 HTML / Markdown 产物，不放在本目录根部；统一放到 `../x 杂七杂八/<事项>/`。
- 判断不清时，优先按“是否会进入需求卡、DESIGN 或原型交付”归类；不会进入的临时分析材料放入杂项事项目录。

## 轻量需求卡口径

需求卡优先回答：

1. 为什么做。
2. 给谁做。
3. 本次做什么。
4. 本次不做什么。
5. 大致怎么做。
6. 怎么验收。

## 需求卡状态

| 状态 | 口径 |
| --- | --- |
| 待梳理 | 需求背景、目标和范围还在收敛，允许保留待确认问题。 |
| 待设计 | 需求口径已基本明确，下一步进入交互和 UI 设计。 |
| 待开发 | 需求和设计均已明确，可以给到开发实现。 |
| 已上线 | 功能已上线，需求卡仅作为历史记录保留。 |
