## 4. 四类数据资源材料

当前用户明确指出需要补充“数据层”，且数据层应对应当前资源里的四类。基于原型，四类资源如下：

| 数据资源 | 当前原型状态 | 页面行为 | 架构含义 |
| --- | --- | --- | --- |
| 文件资料 | 已较完整 | 上传文件、新建文件夹、搜索、筛选、批量操作、预览、OCR 行号、资料树拖拽 | 非结构化资料接入层；需要文件存储、解析任务、OCR、预览文件、文本 / 表格抽取。 |
| 数据库 / 库表 | 已体现 | 添加库表、按库分组、搜索、预览 DDL / 表信息、加入对话引用、批量操作 | 结构化数据接入层；需要数据源连接、库表元数据同步、字段 / 行数据读取、权限隔离。 |
| 数据图谱 | 已体现 | 添加图谱、图谱列表、图谱详情、加入对话引用 | 关系型数据接入层；需要图谱目录、实体关系查询、路径 / 子图能力、图谱上下文供 Agent 使用。 |
| 知识库 | 预留为主 | 资源抽屉中存在知识库类型；交互提示“知识库能力暂未开放” | 制度、规范、案例、风险清单等知识资源层；需要检索、引用、依据约束和版本来源。 |

## 5. 审计作业链路材料

从当前前端原型可归纳出的主链路是：

1. 进入工作台 / 项目空间。
2. 接入或选择资源：文件资料、数据库 / 库表、数据图谱、知识库。
3. 引用或配置技能：公共技能、私有技能、工作台级技能。
4. 通过任务或对话发起分析。
5. 任务进入队列并执行，执行过程可能关联技能、资源和指令。
6. 生成 Markdown 结果，挂到结果树或任务关联文件夹。
7. 结果可编辑、预览、下载、打包、查看历史版本。
8. 对话内容可保存为结果，也可总结为可复用技能。

对应的页面材料：

| 链路节点 | 原型材料 |
| --- | --- |
| 工作台上下文 | `workbenchProjectId`、工作台列表、项目级资料 / 技能 / 结果数据 |
| 资源选择 | 资源抽屉、资源搜索、添加库表 / 图谱、资料上传 |
| 技能配置 | 技能文件、分析规则、关联资料、技能资料匹配 |
| 任务提交 | 创建任务弹窗、任务配置、跑批数据源预览、结果输出位置 |
| 任务执行 | 任务状态：queued / parsing / done / failed；跑批父子任务；打包任务 |
| 结果沉淀 | 结果树、结果文件夹、Markdown 正文、历史版本、引用信息 |
| 二次沉淀 | 保存到结果、总结为技能、生成技能任务 |

## 6. 原型中已经出现的状态与流程信号

| 类型 | 状态 / 流程 | 说明 |
| --- | --- | --- |
| 资料状态 | `queued`、`parsing`、`done`、`failed` | 文件资料需要异步解析，至少存在排队、解析、完成、失败状态。 |
| 任务状态 | `queued`、`parsing`、`done`、`failed` | 任务也存在异步执行状态，和资料解析状态相似但对象不同。 |
| 任务类型 | 单次任务、跑批任务、跑批子任务、生成技能任务、打包下载任务 | 任务服务不能只按“分析任务”建模，需要支持多任务类型。 |
| 结果形态 | Markdown 结果、结果文件夹、任务关联结果、对话产出结果 | 结果不是单纯文件下载，而是可在工作台内组织、编辑和溯源。 |
| 操作确认 | 删除、重跑、创建任务、对话中任务确认 | 部分操作需要确认或配置摘要，尤其是会改变任务 / 结果 / 资源状态的动作。 |
| 技能沉淀 | 对话总结为技能、生成技能任务、保存为工作台级技能 | 技能既是执行输入，也是结果沉淀后的复用资产。 |

## 8. 当前架构图需要重新确认的问题

| 问题 | 为什么需要确认 |
| --- | --- |
| “数据资源层”到底画在“业务服务层”下面，还是作为被业务服务统一管理的独立资源域？ | 当前资源既是工作台页面对象，也是任务 / Agent 执行输入；不能简单放成最底层存储。 |
| “智能执行层”和“四类数据资源层”的调用方向如何表达？ | Agent / 技能执行会消费资源，但资源接入、解析、检索也可能由智能能力参与，方向不是单线。 |
| 是否需要区分“资源管理层”和“数据存储层”？ | 文件、库表、图谱、知识库是资源类型；对象存储、索引、元数据库是底层存储类型，两者不应混为一层。 |
| 技能属于业务应用层、智能执行层，还是单独的技能资产层？ | 技能既有管理页面，又是执行时规则包，还能由结果 / 对话反向生成。 |
| 审计助手是前端模块、业务服务，还是 Agent 编排入口？ | 页面上是中间对话区；后台上可能对应会话、上下文、工具调用和操作确认。 |
| 外部系统 / 数据源是否只放最底层？ | 数据库、图谱、知识库可能来自外部系统，也可能是平台内置资源中心，需要区分“外部来源”和“平台内资源”。 |

## 9. 建议下一步讨论口径

为了避免继续把架构图画成脑图或错误分层，建议先确定以下口径：

1. 架构图类型：业务架构、应用架构、数据架构、技术架构，还是混合的系统架构。
2. 主视角：以“审计作业链路”为主，还是以“系统分层”为主。
3. 数据层表达：是否拆成“数据资源层”和“基础存储 / 索引层”两层。
4. 智能能力表达：是否将 Agent、技能运行时、模型网关、检索引擎放为独立的“智能执行域”。
5. 外部系统表达：是否只表达来源系统，还是也表达模型服务、图谱平台、知识库平台等外部能力。
